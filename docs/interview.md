# g-video 面试问答手册

> 本手册把项目里每个技术点整理成"标准答案 + 预判追问"，全部基于真实实现与实测数据。
> 复习时建议：先自己答，再对照要点；每个数字都要能脱口而出。

## 一、项目总览

### 1. 一分钟介绍这个项目

仿抖音的短视频后端，Go 微服务架构。两个亮点线：
- **完整性**：大文件上传（签名直传+分片+秒传）、异步 HLS 转码、审核后台、推荐流、点赞写合并，从上传到分发到互动全链路；
- **工程深度**：两组压测数据（关注流 N+1 修复 QPS 8.6→474）、testcontainers 集成测试抓到过两个真实 bug、request_id 全链路日志 + Prometheus/Grafana 监控、Docker 一键部署。

### 2. 为什么拆 web-server 和 logic-server 两个服务（BFF）？

- web-server（Gin）：协议转换、JWT 鉴权、限流、参数校验——面向前端变化频繁；
- logic-server（gRPC）：业务逻辑、MySQL/Redis/OSS/MQ 交互——稳定内聚；
- 好处：两边独立扩缩容（web 层常因流量扩、logic 层常因转码/DB 压力扩）；前端协议变化不动业务代码；logic 可被未来的其他 BFF 复用。
- **追问"为什么不做成单体"**：单体也能跑，但这个项目的学习目标就是服务拆分与 gRPC 通信；真实场景里如果团队规模小、流量低，单体+模块化更务实——能这样答说明不是无脑上微服务。

### 3. 为什么服务间用 gRPC？

- 强类型契约（proto 先行，接口即文档）；二进制+HTTP2 多路复用，内网调用开销低；生成代码自带超时/重试/拦截器扩展点。
- 项目里用到的 gRPC 特性：**一元拦截器**（recovery 兜底 panic、访问日志、Prometheus 指标、客户端注入 request_id 到 metadata）、50MB 消息上限配置、GracefulStop。

### 4. 项目的性能数据？

| 接口 | 优化前 | 优化后 |
|------|--------|--------|
| 关注流（300条） | 8.6 QPS / P99 762ms | **474 QPS / P99 77ms** |
| 时间流 Feed | 631 QPS / P99 167ms | **949 QPS / P99 98ms** |
| 热门流（ZSet 预计算） | — | 1143 QPS / P99 98ms |
| 推荐流（三路召回） | — | 691 QPS / P99 174ms |
| 点赞 | — | 1386 QPS / P99 35ms |

环境：本机 Docker 单实例，MySQL 5300 视频。话术要点：主动说明是**单机低配环境、数据用于对比优化前后**，不是标榜绝对值。

## 二、上传与存储

### 5. 大文件上传整体方案？

**双通道**：
- ≤100MB：**OSS 签名直传**——后端签发 15 分钟 PUT 签名 URL，浏览器直接 PUT 到 OSS，文件字节不过应用服务器；
- >100MB：**分片通道**（应用中转）——5MB/片，支持断点续传和秒传。

**追问"为什么 100MB 以上还要走应用服务器"**：签名 PUT 是整对象上传，OSS 上限 5GB；超大文件要浏览器端分片直传需要 STS 临时凭证让前端自己调 OSS 分片 API——这是已识别的演进方向，能讲清楚就好。

### 6. 断点续传原理？

三步协议 init → part → complete：
- init：返回 `upload_id`（OSS 分片会话）+ **已传分片号列表**（OSS ListUploadedParts 查询），客户端跳过已传分片；
- 会话归属存 Redis（24h TTL）：`upload:session:{upload_id}` → {user_id, object_key, md5}，防止用别人的 upload_id 传分片（有集成测试覆盖）；
- 前端把 upload_id 存 localStorage，刷新页面后带着 prev_upload_id 重新 init 即恢复。

### 7. 秒传原理？MD5 碰撞怎么办？

- 前端 spark-md5 增量计算整文件 MD5，init 时服务端查 `videos.file_md5`（有索引），命中则直接复用已有云端对象建新记录，**零字节传输**。
- 碰撞风险：MD5 理论可碰撞，但需人为构造且代价远超收益；生产可升级 SHA-256 或"分片哈希+整文件哈希"两级指纹。这是**演示项目的明确取舍**，答出来反而是加分。

### 8. 对象 Key 为什么用 MD5？

`videos/{md5}.{ext}`——相同内容永远落到同一个对象：秒传天然复用、断点续传天然恢复、同文件去重。代价是同内容不同用户共享存储（业务可接受，正是目的）。

### 9. 布隆过滤器为什么用？多大？误报率？

- 场景：上传 init 的高频指纹查询打到 MySQL。布隆说"**肯定没有**"就直接走新会话，不查库（防穿透）；说"可能有"才查库确认（容忍误报）。
- 参数：Redis 位图 2M bits（256KB）、7 次双重散列（Kirsch-Mitzenmacher：h_i = h1 + i·h2 mod m）；10 万条目理论误报率 ~0.8%，实测 2000 条目 0.000%。
- **无漏报**（加过的一定报"可能有"）；Redis 故障时放行查 DB（正确性优先）。
- 新视频入库即写位图；进程启动全量重建补漏。

## 三、Feed 与推荐流

### 10. Feed 分页怎么做？

时间游标（cursor）：`WHERE created_at < last_time ORDER BY created_at DESC LIMIT 30`，返回 `next_time` 给前端翻页。对比 offset：深翻页不退化、不漏不重（同一时刻插入只影响第一页）。

### 11. 推荐流架构？

三段式：
- **召回**：热门池（ZSet 前 40）+ 最新池（30）+ 关注池（20，登录用户）；
- **排序**：归并取最高分，关注作者 ×1.5 加权；
- **重排**：同作者贪心打散（不相邻）+ 已看过过滤（Redis Set，7 天 TTL，曝光后异步记录）。

### 12. 热度分公式？

`(2×点赞 + 3×评论 + 1) / (小时年龄 + 2)^1.5`——Hacker News 式时间衰减。
- 评论权重(3) > 点赞(2)：评论成本更高、信号更强；
- `+1`：零互动新视频有保底分；`+2` 小时：避免过度惩罚刚发布内容；
- **冷启动**：新内容靠最新池兜底曝光，热度池只装经过验证的内容——朴素的探索利用平衡。

### 13. 热门池怎么保证读一致？

后台协程每分钟：查近 30 天视频 → 写**临时 ZSet** → `RENAME` 原子替换正式 key。读侧任何时刻都看到完整榜单，不存在读到一半的列表；TTL 10 分钟，刷新协程挂掉后榜单自动过期走降级。多实例时分布式锁保证只有一个实例刷新。

### 14. 已看过过滤的存储会不会爆？

Redis Set `user:viewed:{uid}`，7 天 TTL 自动过期；单用户一天刷 500 条 × 7 天 ≈ 3500 个 int64 member，完全可控。

### 15. 打散算法和它的边界？

贪心：相邻同作者就和后面第一个不同作者交换。**鸽巢原理边界**：某作者占比超过一半时必然仍有相邻（数学上不可能全隔开），算法保证相邻对最少化——这一点有单元测试覆盖。

### 16. 怎么评估推荐效果？

分源埋点闭环：Feed 三模式返回时异步累加 `stats:feed:expose:{mode}`；点赞接口带 `source`（前端按当前 Tab 传入）累加 `stats:feed:fav:{source}`；管理员 `GET /admin/stats` 拿到各来源曝光/点赞数，**互动率 = fav/expose 可直接对比 mix vs latest**。

### 17. N+1 是什么？怎么发现和修复的？

- 关注流原实现：查 300 条视频后**循环内每条查一次作者 + 一次点赞计数** = 602 次查询；
- 发现方式：自研压测工具打关注流只有 8.6 QPS / P99 762ms，异常；
- 修复：作者一次 `IN` 查询 + 点赞一次 `IN` 查询 + Map 组装，循环内零 SQL；
- 结果：**QPS ×55、P99 -90%**。这个故事的关键是"压测发现 → 定位 → 修复 → 复测"的完整闭环。

## 四、缓存与高并发

### 18. Redis 在项目里的全部用途？

八处：用户信息缓存、点赞计数增量+落库、上传会话、秒传布隆、热门 ZSet、已看过 Set、集中限流计数、分布式锁。

### 19. 缓存三件套（击穿/穿透/雪崩）分别怎么处理？

- **击穿**（热 key 失效瞬间并发打库）：`singleflight` 合并回源——同 key 并发只有一个请求进 MySQL（用户信息、Feed 首屏两处）；
- **穿透**（查不存在的 key）：秒传前置布隆过滤器；DB 查不到就不写缓存的场景靠布隆拦截；
- **雪崩**（大量 key 同时过期）：TTL 加随机抖动是标准做法；项目里用户缓存 24h 固定 TTL，量级下风险低——如实说明即可。

### 20. 缓存一致性怎么保证？

- 用户信息：cache-aside + 更新资料后**异步 DEL**；容忍短暂陈旧（资料非强一致场景）；
- Feed 首屏：3 秒短 TTL + 发布/审核/删除四处**主动失效**——双保险，短 TTL 兜住遗漏路径；
- **追问"为什么不用延迟双删"**：读多写少 + 短 TTL 已经把不一致窗口压到秒级，延迟双删增加复杂度收益有限。

### 21. 点赞计数为什么写合并？完整流程？

高频点赞如果每次都 `UPDATE videos SET favorite_count=count±1`，DB 行锁成为热点。
流程：
- 写：事务只写 likes 关系行（唯一索引防重）；计数走 Redis `INCRBY video:fav:delta:{id}` + SADD dirty 集合；
- 落库：后台协程每 5 秒 `SMEMBERS dirty → DEL dirty → 逐个 GETDEL delta` → `UPDATE ... GREATEST(favorite_count+delta, 0)`，失败把增量放回下轮重试；
- 读：Feed 展示值 = DB 基数 + 未落库增量（一次 MGET），保证读己之写。
- 效果：单次点赞 DB 写入从 2 次降到 1 次关系行 insert，计数合并成批。

### 22. 为什么 GETDEL 是多实例安全的？顺序为什么是先 INCR 后 SADD？

- GETDEL 原子取走增量：两个 flusher 不会重复落同一个 delta，天然多实例安全（分布式锁只是减少无效竞争）；
- 写路径必须**先 INCR delta 再 SADD dirty**：flusher 是"先取 dirty 后 GETDEL delta"，这个顺序下任何交错都不丢计数；反了就有窗口丢。

### 23. 丢数据窗口？

崩溃时最多丢 5 秒增量。兜底选项：flush 前写 WAL/日志、或缩短窗口。当前取舍：点赞数非资金类，5 秒最终一致业务可接受——**能主动说出这个权衡是关键**。

### 24. 限流怎么做的？

- 方案：Redis **固定窗口**计数（`INCR rl:{scope}:{ip}:{minute}` + EXPIRE），多实例共享配额；登录 5 次/分/IP、上传 100 次/分/IP；
- 降级：Redis 故障自动退回单机令牌桶（x/time/rate），突发容量对齐；
- 为什么登录用 IP 维度：防口令爆破，未登录场景没有用户 ID 可用。

### 25. 分布式锁怎么实现？

`SET key token NX EX ttl` + 释放时 **Lua 比对 token 再删**（防误删他人的锁）。用于热门池刷新和计数落库两个后台协程。**追问"锁过期了任务还没执行完怎么办"**：任务必须幂等（两个协程都是），锁过期导致的重复执行无害；需要严格时用看门狗续期（redsync），当前场景不值得。

## 五、消息队列

### 26. 为什么引入 MQ？哪些场景？

视频发布后要转码 HLS——重且慢，放上传主流程会把用户卡死。发布成功后发 fanout 事件即返回，消费者异步做转码/封面兜底/通知粉丝。解耦 + 削峰 + 失败隔离。

### 27. 消息会丢吗？链路各环节：

- 生产：`DeliveryMode=Persistent` 消息落盘；发送失败只打日志不影响发布（降级：封面同步路径已生成，转码丢失可接受）；
- 存储：交换机/队列 durable；
- 消费：手动 ack，处理成功才 Ack；
- 失败：**指数退避重试 200ms→1s→3s（共 4 次）**，耗尽后 Nack(requeue=false) → 死信交换机 → 死信队列，死信消费者记录消息体和 x-death 头（来源队列/次数/原因）等人工介入——实测验证过全链路。

### 28. 重复消费怎么办？

消费者幂等：封面只在为空时兜底写、HLS 已有切片跳过、重复转码覆盖同 key 对象。幂等是设计出来的，不是靠 MQ 保证的。

### 29. MQ 挂了怎么办？

InitRabbitMQ 失败只降级不 panic（Enabled=false，生产者静默跳过），主服务正常跑——上传/Feed 完全不受影响，只是少了异步转码。有部署级验证。

## 六、可靠性与工程化

### 30. 项目的幂等设计全景？

- 点赞：`(user_id, video_id)` 唯一索引 + OnConflict DoNothing + RowsAffected 判断；
- 上传：MD5 指纹天然去重；分片会话属主校验；
- 评论：同用户+同视频+同内容 5 秒 Redis SETNX 去重（防双击/重试），Redis 故障放行保可用；
- 审核：见下一题的真实 bug。

### 31. 讲一个集成测试抓到的真实 bug（外键删除顺序）

- 现象：新部署的库驳回带点赞的视频必失败，报 MySQL 1451 外键错误；
- 根因：GORM AutoMigrate 给 likes/comments 建了指向 videos 的外键，而代码先删主表 videos 再删子表——顺序反了；
- 为什么之前没暴露：老的手测库恰好没建外键；
- 修复：先删点赞/评论再删视频，驳回/删除两条路径都改，集成测试加了可见性矩阵用例做回归保护。
- 这个故事的价值：**证明测试体系真的在拦 bug，而不是摆设**。

### 32. 再讲一个（审核重复提交）

MySQL 对"值未变"的 UPDATE 受影响行为 0，重复审核已通过的视频被误报"视频不存在"。修复：受影响行 0 时回查视频存在且已是目标状态 → 幂等成功。

### 33. request_id 怎么贯穿的？

web 中间件生成（或透传上游 X-Request-ID）→ 写入 request context → **gRPC 客户端拦截器**注入 metadata `x-request-id` → **服务端拦截器**提取并打进日志。一次请求跨两个服务的日志可完整串联。
**附带的真实坑**：gin 1.12 起 `Context.Value` 默认不委托 request context（`hasRequestContext` 从 `||` 改成了 `&&`），必须显式开 `engine.ContextWithFallback = true`——排查时写了最小复现程序定位到 gin 源码。

### 34. 测试体系？

- 单测：纯函数（热度分公式、打散算法、JWT、URL 解析、布隆散列分布、限流）；
- 集成测试：**testcontainers** 进程内拉起真实 MySQL/Redis 容器；OSS 用本地假服务器模拟——实现了分片上传协议的完整 XML 应答（初始化/传片/列片/合并），CompleteMultipartUpload 全链路可离线测；
- 八条链路：审核可见性矩阵、注册角色安全、上传状态机（含会话属主校验）、计数落库正确性、热门池排序、限流、分布式锁、幂等与分源统计；
- 工程细节：懒初始化（跑单测不启容器）、无 Docker 自动 skip、CI 强制失败防假绿灯。

### 35. 可观测性？

- zap 结构化日志（JSON 可采集），替代裸 fmt.Printf；
- Prometheus：web HTTP 直方图（方法/路径/状态码）+ logic gRPC 直方图（方法/错误码），Grafana 自动 provisioning 四面板（QPS/P99/错误率）；
- pprof：logic :9091 / web :6060，压测时抓火焰图定位瓶颈；
- 健康检查：compose 里 MySQL/RabbitMQ healthcheck + `service_healthy` 条件依赖——解决启动时序问题（logic 起太早 MQ 未就绪）。

### 36. 优雅退出？

SIGTERM → `grpc.GracefulStop()` 排空在途 RPC → 停指标端点 → 关 MQ/Redis → 退出；web 侧 `http.Server.Shutdown(10s)` + 关 gRPC 连接。docker stop 实测日志完整走完三步。

## 七、数据库

### 37. 索引设计？

- `videos(status, created_at)` 复合索引：Feed 查询 `WHERE status=1 AND created_at<? ORDER BY created_at DESC` 完整命中（最左前缀+排序），消除全表 filesort——QPS +50%；
- `likes(user_id, video_id)` 唯一索引：幂等 + 查询；
- `videos.file_md5` 普通索引：秒传点查。

### 38. 软删还是硬删？

视频删除/审核驳回用**硬删**（Unscoped + 先删子表）：需求明确是"物理删除 + OSS 同步清理"；用户用软删（ DeletedAt，可恢复）。按业务语义选，不是全局一刀切。

## 八、部署与协作

### 39. 部署架构？

Docker Compose 10 容器：nginx(前端)/web/logic/MySQL/Redis/RabbitMQ/Prometheus/Grafana。踩过的坑：无 .dockerignore 时构建上下文 131MB（node_modules）导致并行构建 OOM——加 ignore 后几 MB；宿主机端口冲突治理（8081/15674）；healthcheck 编排。CI（GitHub Actions）跑 build/vet/test（含集成测试）+ 前端构建。

### 40. 多实例水平扩展还差什么？（诚实版答案）

已解决：限流集中化、后台任务分布式锁、GETDEL 计数安全。
仍有的单点/假设：MySQL 单实例（主从/代理）、Redis 单实例（哨兵/集群）、gRPC 客户端负载均衡（k8s service 或 grpc-lb）、本地缓存（当前无）。能画出这条演进路线比假装"天然支持水平扩展"可信得多。
